## 第 1 段｜用户问题（0:00–0:40，约 40 秒）

**讲什么**：这东西到底解决谁的什么问题。

**照着说**：

> 政务人员和工作人员排会议时有两个痛点：一是**排会议难**，二是**行程不统一**。  
> 第 2 周我做出来的页面能排、能看。第 3 周我解决的是：**让这张时间线背后有一个真的数据库和真的接口**。  
> 现在的进度是一半通、一半没通——  
> **读已经通了**：打开页面看到的就是数据库里的数据，刷新不会丢（页面启动时会去 fetch `/api/items`）。  
> **写还没通**：在页面上点「+ 新建」、填完保存，只进浏览器内存，**刷新就没了**，不会进数据库。  
> 所以今天我用检查台演示的是：写这条链路在**后端层面是通的**，缺的只是把页面上的保存按钮接上去——那是后面的事。

**动作**：打开 WorkShop 页面（托管首页），点一个色块展示详情 → 再点「+ 新建」填一条并保存，说"这条只活在内存里，F5 之后就没了"。（可选：当场 F5 佐证。）

## 第 2 段｜核心流程（0:40–2:30，约 110 秒）★ 含一次真实写入 + 刷新持久化

**讲什么**：从"页面"到"数据库"这条链路是怎么通的，并当场写一条进去。

**动作顺序（务必按序，别跳）**：

| 步   | 动作                     | 说什么                       | 画面上要让观众看到什么                             |
| --- | ---------------------- | ------------------------- | --------------------------------------- |
| 2.1 | 打开**检查台** URL          | 「这是我这周做的检查台，专门用来证明数据是真是假」 | 页面标题 WorkShop 检查台 · Day 20              |
| 2.2 | 点区块① **重新检查**          | 「先确认后端活着」                 | 绿点 + `{"ok":true,"service":"workshop"}` |
| 2.3 | 点区块② **刷新数据**          | 「这是数据库里真实的事项，不是写死在页面里的」   | 表格列出 items，注意**条数**与最后更新时间              |
| 2.4 | **记下当前条数**（如 12 条）     | 「现在是 12 条，记住这个数」          | ——                                      |
| 2.5 | 点区块③ **执行一次写入测试**      | 「我现在往数据库里真写一条」            | 返回 POST 结果，含新 id                        |
| 2.6 | 回区块② **刷新数据**          | 「写完了，读回来看看」               | **条数变成 13**，新事项出现在列表里                   |
| 2.7 | **按 F5 整页刷新**          | 「关键一步：整页刷新，内存数据会没，数据库不会」  | 页面重载后再点刷新数据，**那条新事项还在**                 |
| 2.8 | 另开标签页直接访问 `/api/items` | 「绕开页面，直接问接口要数据」           | 裸 JSON，同一条数据在里面                         |

**一句话收尾**：

> 写入 → 读回 → 刷新页面 → 数据还在 → 接口也能查到。这条链路证明它不是内存态，是真的落库了。

> **降级预案**：若写入按钮报错，直接展示历史证据——`id 11/12`（09-29 写入）、`id 13/14`（09-30 写入）在今天 10:34 仍被完整读回。**隔天仍能读到 = 持久化已自证**，演示不翻车。

## 第 3 段｜提示词改写过程（2:30–3:40，约 70 秒）

**讲什么**：我不是一句"帮我写个接口"就完事的，中间有几次关键改写。挑 **3 个真实例子**讲。

| 原始说法（模糊）          | 改写后加的约束                                                                                                                                                      | 为什么必须改                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| 「让接口从我建的表里读出真实数据」 | 补：**零依赖直打 PostgREST HTTP API**（不用 `@cloudbase/node-sdk` 的 `app.rdb()`）；显式设 `Accept-Profile` / `Content-Profile` 头；过滤条件走参数化而非拼 SQL；snake_case → camelCase 映射  | 老环境 + 后挂共享集群下，`app.rdb()` 会因取不到 schema 报错；不写清楚，AI 会按常规写法写，部署即炸       |
| 「防止用户重复提交」        | 补：**A 内容去重 + B 幂等键**双保险；A 按 `(title+start_time+end_time+owner_key+table_kind+type)` 查重；B 加 `idempotency_key VARCHAR(64) UNIQUE` 列，冲突返回 **409 且 message 是中文** | 只说"防重复"会得到一种方案，覆盖不全：同内容重试 vs 误点两次是两种场景，得分别拦                          |
| 「把接口代码理一理」        | 补：**控制器只管收请求 / 校验 / dispatch，不得出现任何 fetch；数据访问全部收进 `db.js`**                                                                                                 | "理一理"太虚，AI 可能只调格式。写成硬边界后才能验证：`index.js` 里搜不到 fetch，三处 fetch 全在 db.js |

**照着说**：

> 规律是：**把"想要什么效果"改成"边界在哪、不许怎么做"**。效果描述没法验收，边界描述可以用一条 grep 命令验完。

## 第 4 段｜验证方式（3:40–4:30，约 50 秒）

**讲什么**：我怎么证明它不是我嘴上说的。

**照着做（现场敲，最有说服力）**：

```bash
curl -s https://workshop-d4g02a7z81ff51a63-1d496602788.ap-shanghai.app.tcloudbase.com/api/health
curl -s https://workshop-d4g02a7z81ff51a63-1d496602788.ap-shanghai.app.tcloudbase.com/api/items
```

**三个验收点**：

1. 三条命令都返回 **HTTP 200** —— 公网真的可访问（不是 localhost 自嗨）
2. 响应是 `{"ok":true,"data":[…],"error":null}` —— 形状统一，前端能无脑解析
3. 数据是**从云端数据库读出来的 12+ 条**，不是页面写死的假数据

**再补一句**：

> 完整验收在 `resource/WEEK3_ACCEPTANCE.md`，25 个子项逐条写了验证方法和证据。**17 项 PASS、2 项 FAIL、6 项未执行** —— 没跑过的我标"未执行"，不标 PASS。
